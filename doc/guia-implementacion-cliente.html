Implementacion del LMS corporativo

Documento de orientacion para que una empresa receptora identifique que necesita configurar, donde se cambian las variables y que decisiones debe tomar antes de publicar la plataforma.

Lectura rapida

Sin servidor propio obligatorio Compatible con Firebase Spark Repositorio privado Correo corporativo requiere dominio verificado

El LMS es una aplicacion web estatica. La interfaz se publica como HTML, CSS y JavaScript; la autenticacion y datos viven en Firebase; los paquetes de modulos viven en GitHub privado; Cloudflare Worker actua como gateway seguro para que el navegador nunca vea el token de GitHub.

Para una demostracion se puede operar con dominios y remitentes de prueba. Para produccion, el cliente debe decidir si usara sus propios DNS, dominio web, dominio de correo y repositorio GitHub.

Que debe entregar o decidir el cliente

Dominio web

Ejemplo: lms.empresa.com. Sirve para publicar la plataforma con una direccion corporativa.

DNS

Permite apuntar el dominio web y verificar el dominio de correos si se usara un remitente corporativo.

Dominio de correo

Ejemplo: notificaciones.empresa.com. Permite enviar recuperaciones con identidad corporativa.

GitHub

Repositorio privado donde se guardan modulos, audios, imagenes y certificados.

Firebase

Proyecto para usuarios, login, perfiles, asignaciones, historial y configuracion.

Cloudflare

Worker gateway para proteger el token de GitHub y controlar el acceso a archivos privados.

Rutas de implementacion

Cliente con dominio, DNS y correo propio

Es la ruta recomendada para produccion.

  • Configurar dominio web del LMS.
  • Verificar dominio de correo en Resend u otro proveedor.
  • Actualizar origenes permitidos del Worker.
  • Usar remitente corporativo propio.

Cliente sin dominio o en etapa demo

Es suficiente para validar la propuesta y capacitar internamente.

  • Usar URL local o GitHub Pages para la interfaz.
  • Usar repositorio GitHub privado del proyecto.
  • Mantener Worker en subdominio workers.dev.
  • Usar remitente de prueba si no hay DNS disponible.

Secuencia recomendada de configuracion

  1. Crear infraestructura propia

    Crear proyecto Firebase, repositorio GitHub privado y cuenta Cloudflare. Si habra correo corporativo, verificar dominio en el proveedor de envio.

  2. Actualizar variables del proyecto

    Cambiar .firebaserc, js/firebase-config.js, js/github-config.js y worker/wrangler.toml con los datos del cliente.

  3. Configurar secretos del Worker

    Cargar GITHUB_TOKEN, RESEND_API_KEY y FIREBASE_SERVICE_ACCOUNT_JSON como secretos. Nunca deben guardarse en el navegador ni en el repositorio.

  4. Publicar reglas y gateway

    Desplegar reglas Firestore y publicar el Worker. Verificar que los origenes permitidos coincidan con la URL donde vive el LMS.

  5. Probar acceso inicial

    Crear o validar el administrador inicial, ingresar por DNI, crear usuario de prueba y confirmar recuperacion de contrasena.

  6. Probar modulo completo

    Cargar un modulo, asignarlo, reproducirlo como usuario, completar evaluacion y descargar certificado.

Checklist antes de entregar a produccion

  • Administrador inicial validado.
  • Login por DNI probado con credenciales correctas e incorrectas.
  • Usuario nuevo creado y contrasena actualizada.
  • Recuperacion de contrasena probada.
  • Modulo subido desde panel administrador.
  • Modulo visible desde cuenta usuario.
  • Avance de presentacion controlado por el LMS.
  • Evaluacion y certificado probados.
  • Worker sin secretos en archivos locales.
  • Repositorio GitHub privado confirmado.
  • Reglas Firestore publicadas.
  • Origenes CORS limitados a URLs reales del LMS.
No se recomienda entregar el proyecto con claves descargadas en Escritorio, Descargas, chats o capturas. Los secretos deben vivir solo en Cloudflare Worker Secrets o en el panel del servicio correspondiente.
